# CheckStock — учёт товара между фулфилментами, FBS и FBO

**Веб-приложение** для одного магазина с несколькими складами фулфилмента (ФФ). Показывает физические, доступные и зарезервированные остатки, товар в пути между ФФ, к клиенту (FBS) и на маркетплейс (FBO). Поддерживает журнал операций и обработку повторных подтверждений.

Стек: **Python 3.12, FastAPI, PostgreSQL 16, SQLAlchemy 2 (async), Jinja2, Bootstrap 5, Alembic, pytest, Docker Compose.**

## Быстрый запуск

Требуются Docker Desktop с работающим Docker Engine и Docker Compose. Команды выполнять **из папки `checkstock/`**, где находится `docker-compose.yml`.

В Windows PowerShell:

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
docker compose up --build -d
```

После старта откройте:

- Веб-интерфейс: http://localhost:8000
- Проверка HTTP: http://localhost:8000/health
- Проверка подключения к PostgreSQL: http://localhost:8000/health/db
- Swagger UI: http://localhost:8000/docs

Приложение **автоматически** применяет миграции Alembic и загружает демонстрационные данные при первом запуске. Повторный запуск не должен заново создавать исходные приходы. PostgreSQL хранит данные в именованном Docker volume.

```powershell
# Статус контейнеров и миграций
docker compose ps
docker compose exec web alembic current

# При необходимости — последние сообщения сервера
docker compose logs --tail=80 web
```

Текущая миграция: `002_transfer_cancellation`. Данные PostgreSQL сохраняются в именованном Docker volume. Команда `docker compose down -v` удаляет этот том и не должна использоваться, если необходимо сохранить данные.

> Это локальный прототип без авторизации. Не публикуйте его напрямую в интернет. Пароли в `.env.example` предназначены только для локальной демонстрации; перед любым публичным развёртыванием нужны секреты, аутентификация, HTTPS и ограничения доступа. Bootstrap использует CDN.

## Исходные тестовые данные

Один магазин `demo`, два склада `Север` и `Юг`:

| Артикул | Товар | Север | Юг |
|:--|:--|--:|--:|
| SKU-101 | Органайзер | 10 | 6 |
| SKU-102 | Контейнер | 5 | 0 |
| SKU-103 | Корзина | 0 | 4 |

Всего при первом запуске: **25 шт.** После складских операций остатки будут меняться.

## Возможности

| Раздел | Что можно сделать |
|:--|:--|
| Обзор | Посмотреть остатки и количество в пути по каналам |
| Остатки и товары | Посмотреть все SKU по ФФ, добавить товар, оформить приход |
| Склады | Добавить, переименовать, архивировать склад с сохранением истории |
| Перемещения | Отправить между ФФ, принять или отменить до приёмки |
| Заказы FBS | Зарезервировать товар на конкретном ФФ, отправить или отменить резерв |
| Отправки FBO | Отправить на маркетплейс и подтвердить приёмку |
| История | Посмотреть последние 100 записей (новые сверху) |

Статусы и складские ограничения проверяются **на backend**, а не только в браузере. Формы вызывают API, затем обновляют списки и показатели.

## Учёт и ключевые решения

**На каждом складе:** `available = on_hand - reserved`, где `on_hand` — физический остаток, `reserved` — действующие резервы FBS.

- **Приход:** увеличивает `on_hand` выбранного ФФ.
- **Резерв FBS:** увеличивает `reserved`, не меняя физическое количество; резервирование на выбранном ФФ отклоняется, если там не хватает свободного товара, даже когда на другом ФФ он есть.
- **Отмена резерва FBS:** снимает резерв без изменения `on_hand`.
- **Отправка FBS:** уменьшает `reserved` и `on_hand`; поставка отображается как «к клиенту», пока для неё не предусмотрено завершение доставки.
- **Перемещение:** при отправке уменьшает `on_hand` исходного ФФ и создаёт `in_transit`; при приёмке увеличивает `on_hand` ФФ назначения.
- **Отмена перемещения:** для статуса `in_transit` возвращает количество на ФФ отправления, устанавливает `cancelled` и добавляет запись в журнал. **Использовать только если товар фактически не уехал или физически вернулся**. Если он действительно в дороге — нельзя виртуально возвращать остаток на склад.
- **FBO:** отправка уменьшает физический остаток ФФ; до приёмки товар учитывается в пути, после — как принятый маркетплейсом, **не возвращаясь на ФФ**.
- **Архивирование:** `is_active=false`, склад остаётся в базе с историей и остатками; новые операции запрещаются, уже созданное перемещение можно завершить.

Все изменения остатков, статусов и журнала происходят в **одной транзакции**. Для конкурентных операций применяются row-level locks `SELECT ... FOR UPDATE` и ограничения PostgreSQL, для создания движений — уникальный `request_key` (проверяется идемпотентность). Повторное подтверждение завершённой операции не должно списывать товар повторно. Бизнес-логика находится в `app/services/operations.py`; маршруты в `app/routers/operations.py`; схемы в `app/schemas/operations.py`; чтение остатков — в `app/inventory_read.py`.

Подробнее: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Проверки

Полный набор тестов использует **отдельный контейнер PostgreSQL** и **не очищает рабочий volume**:

```powershell
docker compose --profile test run --build --rm tests
```

Ожидаемый результат проверки: **20 passed** при доступном Docker. Предупреждения библиотек о deprecated API не означают провал тестов. Полные интеграционные тесты проверяют FBS/FBO, перемещения, нехватку, архивирование, отмену, идемпотентность и конкуренцию. Можно остановить тестовый PostgreSQL:

```powershell
docker compose --profile test stop test-db
```

Отдельно предусмотрена **неизменяющая данные** проверка баланса и резервов на рабочей базе (запускать без параллельных операций):

```powershell
docker compose exec web python -m scripts.check_integrity
```

Примеры ручных проверок описаны в [docs/ACCEPTANCE_CHECKLIST.md](docs/ACCEPTANCE_CHECKLIST.md).


## Ограничения прототипа

Без авторизации, ролей, синхронизации с API маркетплейсов и частичной приёмки; нет отдельного события вручения FBS клиенту. Журнал UI показывает последние 100 операций. Отмена перемещения не моделирует физическую доставку; пользователь обязан проверить, где товар фактически находится. Это ограничения текущей версии прототипа.
