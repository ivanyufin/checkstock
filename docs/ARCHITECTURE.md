# Архитектура CheckStock и решения

## Цель

Один артикул может иметь физический остаток на нескольких ФФ, быть заблокирован под FBS или находиться вне ФФ в пути. Основная задача — избежать потери или двойного учёта единиц при смене состояний.

## Архитектурные слои

```text
Браузер (Bootstrap + JS) → FastAPI routes → services/operations.py
                                          ↓
                                SQLAlchemy / PostgreSQL
                                          ↑
                       inventory_read.py → Jinja2 / JSON
```

- `app/models` — физическая модель и ограничения БД.
- `app/services/operations.py` — транзакционные команды.
- `app/inventory_read.py` — вычисляемые показатели для главной страницы.
- `app/routers/operations.py` — HTTP API и валидация входа через Pydantic.
- `app/static/js/app.js` — взаимодействие с API, без изменения запасов на стороне клиента.
- `migrations/versions` — версионирование схемы.

## Сущности

`Store` (один демонстрационный магазин), `Product`, `Warehouse`, `StockBalance` (`on_hand`, `reserved`), `FBSReservation`, `Transfer`, `Shipment`, `StockMovement` (аудит-событие).

`StockBalance` существует только для запасов на ФФ. Товар «в пути» не является физическим остатком ФФ и читается из незавершённых документов `Transfer`/`Shipment`.

## Переходы состояний

| Процесс | Начальное | Действие | Конечное | На балансах ФФ |
|---|---|---|---|---|
| FBS | — | Резерв | active | `reserved += q` |
| FBS | active | Отмена | cancelled | `reserved -= q` |
| FBS | active | Отправка | shipped | `reserved -= q`, `on_hand -= q` |
| Перемещение | — | Отправка | in_transit | `source.on_hand -= q` |
| Перемещение | in_transit | Приёмка | received | `destination.on_hand += q` |
| Перемещение | in_transit | Отмена* | cancelled | `source.on_hand += q` |
| FBO | — | Отправка | in_transit | `on_hand -= q` |
| FBO | in_transit | Приёмка | received | Балансы ФФ не меняются |

*Отмена означает, что груз фактически не покидал ФФ или уже вернулся на исходный ФФ. Если груз в дороге, это действие выполнять нельзя.*

## Инварианты

1. На каждом ФФ для каждого артикула: `on_hand >= reserved >= 0`.
2. Сумма активных FBS-резервов по паре `(warehouse_id, product_id)` равна `StockBalance.reserved`.
3. Для товаров, заведённых через механизм прихода: получено = физически на ФФ + перемещения в пути + FBS в пути + FBO в пути + принято FBO (если не было внешних операций вне текущего прототипа).
4. Движения `StockMovement` не удаляются при архивации склада.
5. Повторное применение уже выполненного статуса не создаёт второго списания.

`StockMovement` — журнал, а `StockBalance` — оперативный агрегат, который обновляется той же транзакцией. Для проверки согласованности есть `scripts.check_integrity`.

## Защита от гонок

- В сервисных командах используется `async with session.begin()`.
- `SELECT FOR UPDATE` фиксирует нужные складские записи и документ перед изменением.
- Отсутствующая ячейка баланса создаётся через PostgreSQL `INSERT ... ON CONFLICT DO NOTHING`.
- Для повторной отправки того же `request_key` применяется `pg_advisory_xact_lock` и уникальные ограничения.
- Если на выбранном ФФ недостаточно доступного товара, операция отклоняется до изменения остатков.

## Выбор интерфейсного стека

Jinja2 и Bootstrap позволяют обслуживать HTML и API одним FastAPI-приложением, сократить число компонентов развёртывания и упростить поддержку компактного интерфейса складского учёта.


## Ограничения и развитие

Прототип без пользователя/прав доступа, реальных маркетплейсов, аудита отдельных сотрудников, частичной приёмки, финальной доставки FBS, полноценного инвентаризационного пересчёта и возвратов. Это не готовая к промышленной эксплуатации WMS.
